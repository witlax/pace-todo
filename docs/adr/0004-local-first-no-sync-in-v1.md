# ADR-0004 本地优先，V1 不做自动同步

- 状态：已接受
- 日期：2026-11-18
- 相关：`docs/01-调研与技术评估.md` 第 5.5 节

## 背景

同步是本项目风险最高的模块：字段级合并、删除与编辑冲突、重复任务实例、习惯补卡冲突，任意一类处理不当都会造成数据丢失。而 V1 的核心价值是"3 秒捕获、今天该做什么、专注有记录"，这些在单机上即可完整成立。

## 决策

- V1 **只读本地数据库**，不要求账号、不联网。
- 提供**手动导出/导入 JSON**（全量快照 + 版本号），作为迁移与备份手段。
- 所有表统一带 `updated_at`、`deleted_at`、`rev`、`device_id` 字段，为后续同步预留，不允许在 V1 之后再加（会引发迁移）。
- V1.5 再以 **WebDAV 双向同步**（坚果云/Nextcloud）作为第一优先级，冲突策略为"字段级 LWW + 冲突副本 + 可见提示"，不做静默覆盖。

## 备选方案

| 方案 | 决策 |
| --- | --- |
| V1 直接上 Supabase/Firebase | 否决：引入登录、隐私承诺、断网不可用，工期 +20 人日以上 |
| V1 上 WebDAV | 延后：可行但会挤占任务/日历/专注的打磨时间 |
| CRDT（参考 Pinch） | 延后：单人单设备场景收益低，复杂度高，字段级 CRDT 与 SQL 查询结合成本大 |
| CalDAV | 延后：作为 V2 的互通能力，而非主同步通道 |

## 后果

正向：

- MVP 工期从约 135 人日压到约 60 人日，可先交付可用版本。
- 无服务端即无运维、无账号体系、无隐私争议。
- 数据完全属于用户，符合差异化定位。

负向：

- 多设备用户需手动导入导出，体验明显弱于滴答清单。
- 预留字段在 V1 期间是"死字段"，需要测试覆盖避免被误清空。
- 后续同步上线时，仍要面对历史数据合并问题（V1 期间单设备，风险可控）。

## 重新评估条件

1. 用户明确要求手机与电脑自动同步（当前已预留实现路径）；
2. 数据量或设备数增长导致手动导入导出不可接受；
3. 出现可靠的本地优先同步基础设施（如 PowerSync/ElectricSQL 在 Flutter 端成熟），可重新评估方案 C。
