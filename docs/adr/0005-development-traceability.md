# ADR-0005 建立四层开发留痕机制

- 状态：已接受
- 日期：2026-11-18

## 背景

项目由 1 人 + AI 协作推进，跨度数月。AI 每次会话不保留上下文，人工也难记住三个月前为何选某个方案、某次构建为何失败。若不强制留痕，会出现三类问题：重复踩坑、决策被无声推翻、线上问题无法定位到改动。

## 决策

建立四层留痕，各司其职：

| 层 | 载体 | 职责 |
| --- | --- | --- |
| L1 | `DEVLOG.md`（只追加） | 操作时间线：环境、依赖、构建、踩坑 |
| L2 | `docs/adr/` | 决策与取舍，不可改结论 |
| L3 | Git 提交 | 代码事实，钩子校验格式与留痕 |
| L4 | `CHANGELOG.md` | 面向使用者的版本变化 |

落地手段：

1. `scripts/devlog.sh <TYPE> "message"` 作为唯一写入入口，保证格式统一。
2. `scripts/setup-hooks.sh` 安装 `commit-msg` 与 `pre-commit` 钩子：前者校验 Conventional Commits，后者在改动依赖/Android/数据库/ADR 时强制同时更新 DEVLOG。
3. ADR 编号单调递增，推翻旧决策只能新增 ADR 并标注取代关系。
4. 每里程碑结束做一次留痕自检（提交数与 DEVLOG 行数比对）。

## 备选方案

| 方案 | 放弃原因 |
| --- | --- |
| 只靠 Git 提交 | 环境变更、构建失败、决策理由无法表达 |
| 只靠聊天记录 | 不可检索、会丢失、AI 会话不持久 |
| 外部 issue/看板 | 增加工具切换成本，且离线不可用 |
| 自动录制全部终端命令 | 噪声极大，含敏感信息，检索成本高于收益 |

## 后果

正向：

- 任意改动可回溯到"何时、何因、如何验证"。
- AI 新会话可通过 DEVLOG + ADR 快速恢复上下文，减少重复解释。
- 强制在敏感改动时留下说明，降低"悄悄改 schema"的风险。

负向：

- 每次操作多一步记录，存在摩擦；通过脚本与钩子把成本降到一行命令。
- 钩子可能阻断提交，需要在规范中明确禁止 `--no-verify`。

## 重新评估条件

1. 团队扩大到 3 人以上，需要引入 issue 跟踪与 PR 流程；
2. DEVLOG 增长到难以检索（超过约 2000 行），需拆分按月归档（归档时保留索引，不删内容）。
