# ADR-0002 使用 Drift + SQLite 作为本地数据层

- 状态：已接受
- 日期：2026-11-18

## 背景

核心数据是任务、清单、标签、习惯打卡、专注记录。典型查询包括：按清单+状态+截止日期过滤、按父任务取子任务、全文搜索标题与备注、按日期聚合统计。数据量预期 1 千至 1 万条任务，习惯记录可达数万行。要求离线可用、迁移可控、查询可组合。

## 决策

使用 **Drift 2.35.4 + SQLite**（`drift_flutter` 打开数据库，`sqlite3_flutter_libs` 提供原生库）：

- 表与查询用 Dart 声明，编译期生成类型安全代码。
- 所有查询以 `Stream` 暴露，UI 订阅即自动刷新（响应式查询）。
- 使用 `schemaVersion` + 显式 `MigrationStrategy`，每次 schema 变更必须写迁移并留痕。
- 标题/备注建立 FTS5 虚拟表，支持前缀与多词搜索。
- 索引按真实查询建：`(list_id, status, due_at)`、`(parent_id)`、`(habit_id, date)` 唯一。

## 备选方案

| 方案 | 放弃原因 |
| --- | --- |
| Hive / Isar（键值/文档） | 复杂过滤与聚合需全量加载后在内存计算，任务量上升后不可控；无 SQL 迁移语义 |
| sqflite 裸写 SQL | 无类型安全、无响应式查询、手写迁移易错 |
| Realm | 许可证与包体积问题；Flutter 端维护活跃度不足 |
| 远程优先（Supabase/Firebase） | 违背"离线优先、免登录"的产品定位；弱网不可用 |

## 后果

正向：

- 复杂筛选可下推到 SQL，1 万条数据量下翻页稳定。
- 响应式查询让"改一个字段刷新整个视图"的成本极低。
- Drift 官方提供全平台待办示例，工程骨架可直接借鉴。

负向：

- 引入 codegen（`build_runner`），首次构建与 CI 时间增加。
- 需要自己维护迁移链，schema 变更成本高于文档数据库。
- WASM/Web 目标需额外配置（本项目暂不需要）。

## 重新评估条件

1. 数据量稳定超过 10 万条且 SQLite 查询出现可复现的性能瓶颈；
2. 需要端到端加密同步，且现有方案无法与字段级合并共存；
3. Web 端成为一等目标。
