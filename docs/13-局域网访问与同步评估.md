# 局域网访问与同步的可行性评估

> 编制：2026-11-23 · 问题：**手机端当后端，电脑通过局域网 IP:端口访问「电脑版布局」**，可行吗？
> 结论先说：**技术上可行，产品上不划算**。下面把可行方案、代价、替代路线拆开写。

---

## 1. 结论

| 方案 | 可行性 | 代价 | 建议 |
| --- | --- | --- | --- |
| A. 手机跑 HTTP 服务 + 提供 Web UI | 可行（Android） | 常驻服务、电量、安全、包体 +15–25MB | 2.x 可选实验功能 |
| B. 手机跑 HTTP API + 电脑装客户端 | 可行 | 要维护第二套客户端 | 不做 |
| C. 不做服务，改用 WebDAV / S3 同步 | 可行且简单 | 只依赖用户已有的网盘/NAS | **推荐** |
| D. iOS 上做同样的事 | 基本不可行 | 系统不允许常驻监听 | 不做 |

---

## 2. 方案 A 长什么样

```
[手机 App]                         [同一 Wi-Fi 下的电脑]
 drift/SQLite  ──►  shelf HTTP      http://192.168.1.23:8080
       ▲              │                     ▲
       └── 手机 UI     └──── HTML/JS ────────┘
```

实现拆解：

| 层 | 做法 | 工作量 |
| --- | --- | --- |
| HTTP 服务 | `shelf` + `shelf_router`，绑定 `0.0.0.0:8080`，前台服务保活 | 2–3 天 |
| 鉴权 | 首次启动生成 16 位 token，二维码/6 位数字码在手机端展示，Web 端输入 | 1 天 |
| 数据接口 | 任务/习惯/专注/目标/日志的 CRUD（复用现有 Repository） | 3–4 天 |
| Web UI | 单页 HTML + 少量 JS（三栏：导航/列表/详情） | 5–8 天 |
| 保活与电量 | 前台服务常驻通知；息屏后进入 Doze 需 `WAKE_LOCK` | 1–2 天 |
| 冲突处理 | 两端并发写，用现有 `rev` 字段做乐观锁 | 1–2 天 |

合计 **2–3 周**，且这 2–3 周只服务「坐在电脑前想用手机数据」这一个场景。

---

## 3. 五个真问题

1. **安全**：局域网不等于可信网络（公司/咖啡厅 Wi-Fi）。必须有 token，且要限制只绑定内网地址；明文 HTTP 意味着同网段抓包可见全部任务内容。要上 HTTPS 就得处理自签证书，浏览器会红屏警告。
2. **常驻成本**：Android 前台服务能保活，但国产 ROM 的省电策略会杀；用户看到的是一条「任务正在运行」的常驻通知。息屏后服务被冻结，电脑就连不上。
3. **包体**：如果走 Flutter Web 复用现有 UI，需要把 `main.dart.js` + CanvasKit 打进 APK（+15–25MB），而 Web 端拿不到 drift 的原生 sqlite，所有数据必须走 HTTP——等于「同一套 UI，两套数据通道」。
4. **状态不一致**：手机上刚勾完，电脑页面还显示未完成。要么轮询（耗电），要么 WebSocket 推送（更多代码）。
5. **维护面**：多一个 HTTP 层、多一个 Web UI、多一套鉴权，每个新功能都要做两遍界面。

---

## 4. 更划算的替代：WebDAV / S3 备份同步

用户已经明确放弃 CalDAV，后期考虑 WebDAV/S3——这条路比「手机当服务器」简单一个数量级：

| 维度 | 手机当服务器 | WebDAV / S3 同步 |
| --- | --- | --- |
| 网络方向 | 需要入站连接 + 固定内网 IP | 只需要出站 HTTPS（用户自己的网盘） |
| 常驻 | 必须 | 不需要，按需同步 |
| 安全 | 自建鉴权 + 明文风险 | 复用网盘账号 / AccessKey，TLS 由服务方保证 |
| 数据模型 | 需要 API + 冲突协议 | 复用现有 zip / JSON 备份包，按文件版本比较 |
| 工作量 | 2–3 周 | 3–5 天（上传/下载 + 冲突提示） |
| 跨平台 | 仅 Android | Android + Windows + 未来的 iOS |

**推荐的同步实现（V2 第一优先）**：

1. 设置里填 WebDAV 地址 / 账号 / 应用密码，或 S3 的 endpoint / bucket / AK / SK；
2. 「立即同步」= 导出 zip 备份包 → 上传为 `tasks-<deviceId>-<timestamp>.zip`；
3. 恢复 = 列出远端包 → 选一个 → 覆盖导入（沿用现有 `importZipBytes`，已有附件数量校验）；
4. 不做双向合并：本地优先的定位下，「谁后同步谁覆盖」+ 明确的提示语就够，双向合并是 2.x 之后的独立课题。

这样「在电脑上看手机的数据」也能做到：Windows 版直接读同一个网盘目录的备份包。

---

## 5. 如果一定要局域网，最省的做法

不做 HTTP 服务，改成「局域网导出」：

- 设置 → 导出 → 选择「局域网分享」，生成一次性下载链接（用一个临时 HTTP server，导出完自动关闭）；
- 电脑浏览器打开 `http://手机IP:端口/backup.zip` 下载即可。

代码量约 1–2 天，只在导出时开服务（无常驻、无鉴权压力、无电量问题），能满足「把数据拿到电脑上」的真实需求。

---

## 6. 结论与建议

- **不建议**把「手机当后端 + 电脑浏览器访问」作为产品能力：2–3 周换一个低频场景，还要长期维护两套 UI。
- **建议**按顺序做：① WebDAV/S3 备份同步（3–5 天）→ ② 局域网一次性导出（1–2 天）→ ③ 若确有强需求，再评估常驻服务。
- Windows 桌面版本身已经是「电脑版布局」，本地数据互通靠备份包即可，不需要网络层。
